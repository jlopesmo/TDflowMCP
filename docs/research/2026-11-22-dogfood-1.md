# Dogfood round 1: Claude Code doing real work through TDflowMCP (2026-11-22)

**Owner priority D15:** before Phase 2A, use TDflowMCP with a coding agent in a disposable TouchDesigner project. Inspect networks, modify permitted operators, verify the results, and exercise undo and session logs. Develop source-first with isolated candidate `.tox` builds; the live instance must never modify its own protected internals. Report usability problems, missing capabilities and friction.

**Setup:**
- Tooling: `python -I tests/td/run_td_dogfood.py`; TouchDesigner 2025.32440; Claude Code 2.1.289.
- Project: a disposable project with a realistic network: `noise1 → level1 → out`, a Constant CHOP, tagged and untagged data DATs, an Execute DAT, a `tdflowProject` COMP and the TDflowMCP component.
- Agent: builder token on `/project1/fx/**`; the project-scope `tdflow-core` Skill was installed through the consent flow.
- Connection: the generated JSON entry, `--strict-mcp-config`, only the 16 TDflowMCP tools plus `Skill` allowed, the token in the environment only.
- Sessions: five independent sessions per pass, with the tasks in the table below.

- **Pass 2, in TD:** 6/6 + 35/35. Audit: 109 events, the chain verifies, 0 unaccounted executions. OnFrame p99 0.21 ms during agent work (from `build/td-dogfood-results.json`).
- **Isolation, corrected after review 8:**
  - Passes 1–3 used `--strict-mcp-config` and `--allowedTools`. `--allowedTools` only pre-approves tools, so the built-in write/shell tools existed in those sessions. Their logs show no call to them.
  - Those sessions ran inside the repository folder (`.tmp/`) with session persistence.
  - The harness now isolates Claude Code fully: the working directory is outside the repo; `--tools Skill,ToolSearch`, `--setting-sources project` (the disposable project's settings only; `--restricted` was rejected because it also hides project Skills), `--permission-mode default`, `--disallowedTools` and `--no-session-persistence` are set; and the tool list is asserted from the init message (pass 4).
- **Wall-clock time:** the model dominates, with API time 34–40 s of the 38–47 s per task. TDflowMCP adds about 1–2 s per task (≈ 83 ms × 10–25 calls). **SQLite latency is not a usability problem**, consistent with owner D15 and [B6](../../spikes/b6/README.md).

## Problems found, and what was done

| # | Kind | Finding | Status |
|---|---|---|---|
| 1 | **Bug** | `tdflow_get_parameters` with a `page` filter failed with `INTERNAL_ERROR` on a Level TOP: a parameter without a page object raised outside the per-attribute guard | **Fixed** (robust page lookup); in-TD regression `dogfood.page_filter_works` |
| 2 | **Misleading result** | `get_errors` said "no problems" for operators that had never cooked. TD fills `errors()` only after a cook, so a later session saw `dat_sink`'s error. The agent first reported "no errors" | **Fixed without forcing cooks** (a cook can evaluate expressions or scripts): `get_errors` lists `never_cooked` with a note; `get_operator` returns `cook_count`. In pass 3 the agent stated the caveat correctly. Regressions `dogfood.get_errors_reports_never_cooked`, `dogfood.get_operator_cook_count` |
| 3 | Friction | To read one parameter, the agent paged with `offset`/`limit` | **Added** `names` filter to `get_parameters` (optional, ≤ 50); regression `dogfood.names_filter` |
| 4 | Friction | Wiring had to be learned with one `get_operator` per child; new nodes had no sensible position | **Added** `inputs` and `x`/`y` to each `list_operators` row, and `x`/`y` to `get_operator`; regression `dogfood.list_has_inputs_and_position` |
| 5 | Missing capability | Describing a network still needs one call per operator (flags, errors, non-default parameters) | Proposed: a bounded, read-only `tdflow_describe_network` (Phase 2B tool candidates) |
| 6 | Friction | A four-step edit (create, disconnect, connect ×2) is four separate undo steps; undo reverts only the newest step | Recorded. Grouped changes ("change sets") need an undo-semantics spike (S4 showed TD undo blocks per call) |
| 7 | Friction | Claude Code's deferred tools mean each session starts with a `ToolSearch` before the first TDflowMCP call | Client behaviour; no action |
| 8 | Wording | An expression denial reads "role builder has no execute permission" (R1); the Skill explains that approvals are unavailable | Recorded: consider naming `APPROVAL_UNAVAILABLE` earlier in the message |
| 9 | Missing capability | Agents cannot see what the user is looking at (selected or current operator) or cook/performance data | 2B candidates (`tdflow_cook_performance` is already listed) |

# TDflowMCP v1.3 visual diagnostics

Development is owner-authorized. Release requires passive-read safety, independent review, complete packaged acceptance, compatibility approval where required, and the hosted release checks.

## Verified v1.2.0 baseline

The disposable diagnostic fixture ran against the published v1.2.0 binary on Windows with TouchDesigner 2025.32440. All 46 checks passed. It used real loopback MCP calls and independently forced a cook after each authorized repair to verify the resulting output.

| Scenario | Observed v1.2 outcome | Diagnostic gap |
|---|---|---|
| Broken visual output | Network and operator inspection exposed an error and empty input list. Parameter inspection exposed the stored expression. The approved replacement and normal wire edit restored output. | The caller correlated separate results and interpreted missing input evidence. |
| Controlled cook cost | The last CPU cook took 12.5138 ms on the expensive fixture and 7.5679 ms on the comparison operator. | Timings appeared in operator rows and threshold-based hints. Their recency and coverage were unclear. |
| Visual mismatch | Two cached 256×256 captures differed. The unlocked output was refused. | The caller compared two captures across the rate limit. The server supplied no aligned pixel metric. |
| Regression | Network inspection found the broken output. Reconnecting the original source restored pixels and kept the unrelated fixture intact. | The caller used the existing inspect, repair and verify workflow. |

Cook and callback counters stayed unchanged during diagnostic reads. An owner-only cached pixel probe over a locked texture with an executable upstream fixture also preserved both counters. [Validation](../icm/validation-index.md#v130-diagnostic-baseline)

## Candidate scope

- Extend network description with opt-in findings, readable upstream leads and ranked last CPU cook samples.
- Compare two permitted, cached owner-locked outputs with bounded RGB measurements. Match the established runtime and bypass guard and verify the read path passively.
- Guide agents through evidence, a minimal authorized change, and post-repair verification. Active profiling, broader TOP inspection and Script operator lifecycle authoring remain outside this milestone.

## Release acceptance

Replay A–D and exercise the visual eligibility, protected-path, audit and stale-target gates. Check for unexpected cooking or callbacks. Run packaged regressions, live clients, independent security and usability review, and Windows and Ubuntu CI. Verify the actual tagged binary and five public downloads. [Release procedure](../operations/verification-and-release.md)

The first candidate passed all four workflows. It exposed the required input in A, ranked the measured CPU samples in B, quantified the aligned RGB difference in C, and verified restored wiring and pixels in D. A needed one owner approval for the expression change. Both live assessments missed that secondary expression fault while diagnosing the empty input, so the repair replay checks each condition independently. | Scenario | v1.2 workflow | v1.3 workflow |
|---|---|---|
| A | Eight MCP calls included a separate error query, operator and named parameter reads, approval replay, wiring and verification. | Seven calls supplied the same workflow with missing input evidence in the first network response. |

## Proposed Script operator lifecycle

The v1.1 probes found factory callback DATs and cook-triggered execution. Script operators can also consult the callback DAT for cook policy and parameter pulses. A supported lifecycle requires an isolated staging project, an exact operator-to-authored-DAT association, and control over the declared inputs. Staging keeps the code inactive while it is stored and inspected as authored text. Activation would bind the exact source, callback association, input topology, runtime and cook trigger to approval. Recovery would disable subsequent callbacks and restore a saved disposable project or staged copy before reopening it. Approved Python retains host access even inside a disposable project.

A cook-disabled parent demonstrated staging in the v1.1 probe. It does not establish a boundary for every runtime callback, owner edit or transfer into an active network. Keep Script CHOP, SOP and TOP out of the creation allowlist until the activation, ownership and recovery design can be proven and the required owner decision is recorded. The supported v1.2 workflows use the existing approved expression and Execute DAT paths.

A v1.2 owner-driven probe measured zero cooks and callback executions for all three staged operator families. Owner activation and forced cook yielded one cook and one callback per operator. This confirms the narrow observed sequence and does not provide a complete activation boundary.

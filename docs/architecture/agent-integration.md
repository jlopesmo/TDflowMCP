## 1. Client registry

`src/integrations/clients.json` (implemented, embedded in the `.tox` as the `clients` DAT) — one entry per coding agent. The design sketch below is superseded by the file; notable verified facts: Claude Code needs `"type": "http"` in JSON entries and expands `${VAR}` in `headers`; Cursor uses `${env:NAME}`; Codex uses `http_headers_helper` (automatic setup, Windows) or `bearer_token_env_var` (manual); VS Code Copilot's native file is `~/.copilot/mcp-config.json` with `${NAME}`. The MCP 2026-07-28 list results must carry `ttlMs`/`cacheScope` (found by the live test):

```json
{ "id": "claude-code", "display": "Claude Code", "support": "primary",
  "mcp": { "transport": "http", "add_command": "claude mcp add --transport http --scope user tdflow {url} --header 'Authorization: Bearer ${TDFLOW_TOKEN}'" },
  "skills": { "format": "skill-md", "project_dir": ".claude/skills", "user_dir": "~/.claude/skills" },
  "verified": { "client_version": null, "date": null, "evidence": null } }
```

**Selection and Auto (D21, revised by owner D22, implemented).**
- **The Coding Agent menu** (Auto, Claude Code, OpenAI Codex, Cursor, VS Code Copilot, Other MCP Client) picks which client to connect and whose instructions to show. It never changes the protocol or permissions.
- **Auto** discovery is read-only (`connect.discover`):
  - names on PATH (`shutil.which`);
  - extension folder names (`anthropic.claude-code-*`, `openai.chatgpt-*`, `github.copilot*` under `.vscode`, `.vscode-insiders`, `.cursor`, `.windsurf`) and configuration folders.
  - It never runs anything and never reports paths.
  - One found: that client. Several found: Connect Agent asks which one, and each gets its own identity, credential, permissions and status. None found: the generic `other` entry.
  - Codex is one row for its CLI, its editor extensions and its configuration folder, because they share `~/.codex/config.toml`. The extension's version is read from its folder name. The Codex desktop app is not listed separately: no install marker was verified.
- **Grok** is not listed: no compatible MCP client and configuration method has been verified, and a model is not a client.

**Consent-based connection (owner D22, [ADR-0015](../decisions/0015-consent-based-client-connection.md), implemented).**
- **Claude Code** (CLI and VS Code extension share `~/.claude.json`): after the user approves the plan in TouchDesigner, TDflowMCP writes one user-scope entry: `mcpServers.tdflow` = `{type: http, url, headersHelper}`.
  - The helper is a fixed PowerShell (Windows) or sh (macOS) command. It reads this project's token from the OS-protected store, for the project that `/.well-known/tdflowmcp` names (`connect`).
  - No token is in the file, a command line or the environment.
  - Verified on Windows with the CLI 2.1.289 and the extension's engine 2.1.330; macOS not validated.
- **Codex on Windows** (owner D27, [ADR-0017](../decisions/0017-codex-one-click-connection.md); the CLI, the IDE extension and the desktop app share `~/.codex/config.toml`): after the same approval, TDflowMCP adds one table: `[mcp_servers.tdflow]` with `url` and `http_headers_helper`.
  - The helper is the same fixed PowerShell command with the same vault and listener proof, in its own credential slot. On any failure it exits with status 1 and prints nothing, because Codex treats an empty header object as "connect without credentials".
  - The file is edited as text: only that table is added, updated or removed, every other byte is kept, and the result is re-parsed and compared before it is written. Layouts TDflowMCP does not edit are refused (`CONFIG_UNSUPPORTED`).
  - Codex and Claude Code can both be connected to one project; each has its own agent, key, permissions and audit records.
  - A running Codex picks up a repaired key by itself (it runs the helper again after a 401).
  - Verified on Windows with the Codex CLI 0.160.0 and the VS Code extension 26.1120.50957 (engine 0.171.0-alpha.13.2). Not offered on macOS or Linux, and not for Codex in a remote or cloud environment.
- **Cursor, VS Code Copilot, Other, and Codex where automatic setup is not available:** a manual fallback, with the limitation stated in the instructions. Copy Token, one shell command for the variable, one registration command or entry. These clients only offer an environment variable present at start, or OAuth (not offered).
- The audits and per-client tables are in the records for [Claude Code](../research/2026-11-24-one-click-connection.md#client-audit) and [Codex](../research/2026-11-25-codex-one-click-connection.md#what-codex-documents-and-what-was-observed).
- **Connected client identity:** the Connected Agents line shows the client's self-declared name and version. Modern-era clients (Claude Code) send them with each call; legacy-era clients (Codex: `codex-mcp-client`, protocol 2025-06-18) send them only in `initialize`, where they are now recorded. The text is bounded, allowlisted and never trusted.

Support levels: `primary` (tested each release), `verified` (tested once, date recorded), `documented` (from vendor docs only), `generic` (the `other` entry), `unsupported`. A client is never shown as `verified` without a recorded test in `validation-index.md`. Example values above are **placeholders to verify**.

## 2. Skills bundle

- Source: `src/skills/<skill-name>/SKILL.md` (+ references), versioned with the tool surface (`skill_version == tool_surface_version` major.minor).
- Content: how to use TDflowMCP tools safely, the scope/permission model as seen by agents, checkpoint/handoff etiquette (2A), and "never install or reconfigure without asking the user".
- Skills are guidance, **not enforcement** — every rule they describe is also enforced (or explicitly unenforced) by the server.
- Upstream Skills (e.g. TDMCPSkills) are not copied, because they carry the TDMCP Shared Use License ([ADR-0008](../decisions/0008-upstream-reuse-policy.md)). TDflowMCP Skills are authored independently.
- **Namespace and coexistence:** TDflowMCP Skills use the `tdflow-` prefix. TDMCPSkills reserves `td-` and manages its own `.tdmcp-skills.json` manifest ([TDMCPSkills README](https://github.com/TouchDesigner/TDMCPSkills/blob/2025.30000/README.md)). TDflowMCP never reads, modifies or removes `td-*` skills or that manifest, and its own manifest is a separate file.
- **No network:** the Skills bundle is embedded in the `.tox`, so installing or updating works offline. TDMCP, by contrast, fetches Skills from its latest release by default.

## 3. Client-aware installation (consent-first)

**MCP client connection** is consent-based for Claude Code and, on Windows, Codex ([ADR-0015](../decisions/0015-consent-based-client-connection.md), [ADR-0017](../decisions/0017-codex-one-click-connection.md): one previewed, approved, reversible entry; never silent) and instruction-only for every other client ([security model §10](security-model.md#10-setup-assistant-and-integration-safety)). For **Skills files**, there are two modes, chosen per action by the user in the Setup Assistant:

1. **Instruction mode (default):** show exact commands/files to copy; TDflowMCP writes nothing.
2. **Assisted write:** requires a paired admin session. TDflowMCP shows the target path (project or user scope, user-chosen), a full preview/diff, and the file list with hashes; writes only after explicit confirmation; records `tdflow-skills.manifest.json` in the target (`{skill, version, files: {path: sha256}, installed_at, installed_by: "TDflowMCP <version>"}`).

Hard rules:
- Targets are restricted to the skills directories listed for the chosen client in the registry (project or user scope). Arbitrary paths are not allowed.
- Paths containing `..`, symlinks or junctions anywhere in the target are rejected.
- Writes are atomic: write to a temp file, then rename.
- Bundled Skills are verified against the `TDflowMCP.json` build manifest hashes before writing, because Skills steer agents.
- Never overwrite a file whose hash doesn't match the manifest (user-modified → show diff, stop); never write tokens into any file; never write client permission/approval settings (contrast: Envoy writes `.claude/settings.local.json`); never write inside a Git repository without telling the user it will appear in `git status`; uninstall removes only manifest-listed, unmodified files. Every write is audited.

## 4. Version management

Skill 1.9 introduces evidence-first diagnostic guidance. Copy Agent Prompt asks agents to show evidence and verify fixes. The tool-surface major version stays `1`.

Skill 1.10 guides agents to retain a change's audit sequence, bind undo to that exact change, and inspect the result. [v1.4 milestone](../milestones/v1.4-workflow-recovery.md)

- `tdflow_whoami` returns `server_version`, `tool_surface_version`, `expected_skill_version`.
- **Skill 1.1 (Phase 2A):** adds the project-memory workflow (resume before changing, checkpoint, handoff with checkable claims, the memory error codes). The tool surface stays `1` because the change is additive.
- **Skill 1.2 (Phase 2A increment 3):** adds default placement of created operators, the optional handoff `status`, `fingerprint.parameter_changes` on resume, and repository-mode memory (`memory.authority`, the repository-memory permission, `MEMORY_LINK_MISMATCH`). Additive again, so the tool surface stays `1`.
- **Skill 1.6 (D25, [ADR-0016](../decisions/0016-capabilities-page-and-permission-editing.md)):** §1a "What can you do?": answer from `tdflow_capabilities` (your own effective access, never TDflowMCP's feature list), and send the user to Open Dashboard in TouchDesigner for the Capabilities page; never open the dashboard, request a pairing or change your own permissions. The full instructions and the Copy Agent Prompt say the same. Additive, so the tool surface stays `1`.
- **Skill 1.7 (v1.1)** documents expression source inspection, Python DAT syntax and diff previews, inactive callback editing, separate activation approval and runtime output checks. It directs agents to leave TOP locks to the owner and explains the runtime restriction on capture. Copy Agent Prompt introduces the workflow after connection and scopes have been checked. Existing tool names and tool-surface version `1` are retained.
- **Skill 1.8 (v1.2)** adds local operator discovery, approval for custom controls and their expressions, and native Base COMP TOP outputs. Copy Agent Prompt points agents to the workflow. Setup and client connection follow the existing consent flow.
- **Skill 1.3 (Phase 2B):** the approval flow (`APPROVAL_REQUIRED`, tell the user, repeat the identical call once approved, never loop or work around a denial) and the operator role.
- Skills declare their version and instruct the agent to compare it and tell the user on mismatch. **Verified in 1C:** Claude Code ignores unknown frontmatter fields and documents `metadata`, so the version is `metadata.tdflow-skill-version`, repeated in the skill body and recorded in the install manifest. The live test showed the agent reading both the project Skill's version and `expected_skill_version`.
- The Setup Assistant compares installed manifests with the bundled version and offers update (same consent flow).
- **Coexistence with TDMCP:** TDMCP defaults to port 13316, and a Claude account plugin may already connect there. TDflowMCP uses 9480 and the server name `tdflow`, so both can be registered in the same client without colliding. Running both against the same project is allowed but not recommended, and the Setup Assistant warns about it if it detects another MCP component.
- MCP client config drift: for a connection made by Connect Agent, the entry is re-checked a few seconds after the write, and Connect Agent or Repair Connection recomputes the plan (a changed port becomes an `update`). Otherwise drift is detected only from failed connections. TDflowMCP reads a client's configuration file only to plan a connection the user started.
